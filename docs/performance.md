# 성능 점검

## 기준 (Pleos 성능·리소스 가이드, 심사 기준)

| 항목 | 기준 |
|---|---|
| CPU, 주행 중, 비내비 앱 | 5% 미만 |
| CPU, 정차 중 | 25% 이하 |
| RAM | 400MB 이하 |
| 앱 실행 / 콘텐츠 로드 | 각각 10초 이내 |
| 버튼 반응 | 2초 이내, 넘으면 진행 표시 |

## 측정 방법

`scripts/measure-performance.sh`가 아래를 자동으로 한다. 에뮬레이터를 켜고, 앱을 설치·동의한 뒤, `adb forward tcp:8088 tcp:8088`을 해 두고 실행한다.

- **차량 이벤트:** Virtual Console의 REST API(`PUT /vehicle/hvac?driver_seat=…`, `?ac=…`)로 2초마다 하나씩 바꾼다(시트 열선·통풍 단계, 에어컨). 사람이 클릭하지 않아 매번 같은 부하가 된다.
- **주행:** `PUT /vehicle/gear?gear=Drive`와 `PUT /vehicle/controls?speed=15…` → CarDrivingState가 moving, UX 제한 DO=true.
- **CPU:** `/proc/<pid>/stat`의 utime+stime(틱, 100Hz)을 2초마다 읽는다. 평균은 시나리오 전체, 최대는 가장 바쁜 2초 구간이다. 기준이 코어 하나 기준인지 전체 기준인지 문서에 없어, 코어 하나 기준 값과 전체(코어 수로 나눈) 값을 함께 적는다. 판정은 더 엄격한 코어 하나 기준으로 한다.
- **메모리:** 각 시나리오 끝에 `dumpsys meminfo <pid>`의 TOTAL PSS.
- **실행 시간:** `am force-stop` 후 `am start -W`의 TotalTime(콜드) 3회, 다른 앱을 띄운 뒤 다시 여는 웜 3회.
- **빌드:** 제출 형태와 같은 `prodRelease`(R8 축소, 로그 제거). 설치를 위해 디버그 키로만 서명했다(`-PdebugSignedRelease`).

## 결과

2026-11-03, Pleos Car 에뮬레이터(arm64, Android 14, 4코어), `prodRelease` 0.3.0(debuggable=0). 동의 후 수집 중인 상태.

| 시나리오 | 앱이 받은 이벤트 | CPU 평균, 코어 하나 (전체) | CPU 최대 2초, 코어 하나 (전체) | CPU 시간 | PSS |
|---|---|---|---|---|---|
| 정차, 앱 백그라운드, 이벤트 없음 (60초) | 15 | 0.00% (0.000%) | 0.00% (0.000%) | 0.00초 | 43MB |
| 정차, 앱 백그라운드, 2초마다 이벤트 (60초) | 42 | 0.02% (0.004%) | 0.48% (0.120%) | 0.01초 | 47MB |
| 주행, 앱 백그라운드, 2초마다 이벤트 (120초) | 88 | 0.02% (0.004%) | 0.48% (0.119%) | 0.02초 | 47MB |

"앱이 받은 이벤트"는 Vehicle Service가 이 앱으로 보낸 속성 콜백 수다(logcat `broadcastPropertyCallback`). 이벤트 없는 시나리오에도 숫자가 있는 건 속도·기어 같은 주기 신호 때문이다.

| 실행 | 1회 | 2회 | 3회 |
|---|---|---|---|
| 콜드 (`am force-stop` 후) | 168ms | 178ms | 159ms |
| 웜 (다른 앱을 띄운 뒤) | 66ms | 43ms | 44ms |

**판정**

| 항목 | 기준 | 측정 최댓값 | 결과 |
|---|---|---|---|
| CPU, 주행 중 | 5% 미만 | 평균 0.03%, 2초 최대 0.48% (코어 하나) | 통과 |
| CPU, 정차 중 | 25% 이하 | 평균 5.67%, 2초 최대 9.95% (코어 하나, 월을 2초마다 넘기는 최악의 조작) | 통과 |
| RAM | 400MB 이하 | 57MB | 통과 |
| 앱 실행 | 10초 이내 | 178ms | 통과 |
| 콘텐츠 로드 | 10초 이내 | 고지서 첫 표시는 실행 시간 안에 끝남. 합성 데이터 두 달치 생성·저장·표시는 약 1초 (demo 빌드) | 통과 |
| 버튼 반응 | 2초 이내 | 월 이동·설정 토글은 즉시 반영. 오래 걸릴 수 있는 작업(기록 지우기, 합성 데이터)은 진행 표시 | 통과 |

**다른 앱을 여러 개 띄웠을 때:** 설정, 지도, 미디어, 전화, 차량 제어를 차례로 띄운 뒤에도 PID가 그대로였고 포그라운드 서비스가 유지됐다. 그동안 Activity는 STOPPED였고 Virtual Console로 바꾼 7건이 전달·기록됐다.

**처음 측정을 버린 이유:** 첫 실행에서는 Virtual Console이 `503 emulator_inactive`를 돌려줘 이벤트가 하나도 적용되지 않았다. 브라우저 세션이 만료됐기 때문이다. 그래서 수치가 실제보다 낮게(대부분 0%) 나왔다. 스크립트가 이제 세션을 1초마다 유지하고, HTTP 응답 코드를 확인하고, 앱이 받은 이벤트 수를 함께 적는다. 위 표는 다시 잰 값이다.

**한계**

- 에뮬레이터 수치다. 실차 SoC와 Vehicle Service의 이벤트 빈도는 다를 수 있다.
- 기준이 코어 하나 기준인지 전체 기준인지 문서에 없다. 둘 다 적었고 엄격한 쪽으로 판정했다(주최 측 확인 필요).
- Room 일괄 저장(60초)과 하트비트(60초)는 백그라운드 시나리오 안에 포함돼 있다.
